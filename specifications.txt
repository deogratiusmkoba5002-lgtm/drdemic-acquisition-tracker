DrDemic Acquisition Tracker
Software Requirements and Development Guide
Project type: Personal school acquisition management system
Primary purpose: Organize school acquisition activities, manage appointments, track relationships with schools, and support the growth of DrDemic.
Development approach: Incremental development, manual coding, and continuous testing.
Initial platform: Local web application.
Proposed technology stack: Python, Flask, SQLite, HTML, CSS, and JavaScript.
 
1. Project Overview
DrDemic Acquisition Tracker is a lightweight application designed to help the founder manage the process of acquiring schools as customers for DrDemic.
The application must organize information about schools, track their acquisition status, manage appointments, and display important upcoming events.
The system must remain simple enough to operate during a busy working day.
The founder may visit several schools, have unexpected conversations, arrange appointments, conduct demonstrations, and follow up with decision-makers. The application must support these activities without requiring lengthy data-entry sessions.
The system is intended primarily for individual use. It does not initially require multiple user accounts, employee management, advanced analytics, or machine learning.
1.1 Core objectives
The system must:
1.	Maintain a centralized list of schools being approached.
2.	Store essential information about each school.
3.	Track the current relationship between DrDemic and each school.
4.	Manage appointments and follow-up activities.
5.	Display nearby upcoming events on the dashboard.
6.	Alert the founder when an appointment or follow-up is approaching.
7.	Distinguish prospects from schools that have become paying customers.
8.	Minimize the amount of information the founder must enter manually.
1.2 Design philosophy
The application must follow five principles.
Simplicity: Every feature must have a clear purpose.
Minimal data entry: Store only information that helps the founder make decisions or take action.
Fast operation: Recording a school visit should take approximately 30 seconds to two minutes in ordinary circumstances.
Action-oriented interface: The dashboard should emphasize what requires attention now or soon.
Incremental development: Implement and test the essential features before introducing additional functionality.
 
2. Application Structure
The application will contain four main sections:
1.	Dashboard
2.	My Schools
3.	Appointments
4.	Settings
The navigation should remain visible and consistent throughout the application.
2.1 Dashboard
The dashboard is the application's main screen.
Its purpose is to answer three questions:
•	What needs my attention today?
•	Which appointments are coming up?
•	Which schools am I currently trying to acquire?
The dashboard must not display every school, every historical visit, or every appointment ever created.
It should display only the information relevant to the current period.
A. Summary cards
At the top of the dashboard, display a small number of summary cards.
Schools Approached
•	Number of schools currently in the acquisition process.
Appointments
•	Number of upcoming appointments within the dashboard's display window.
Follow-ups Due
•	Number of schools requiring follow-up today or earlier.
Paying Customers
•	Number of schools currently classified as paying customers.
Each card should be clickable when it provides a useful shortcut to the relevant section.
B. Upcoming events
Display a section titled "Upcoming Events."
It should contain appointments and scheduled follow-ups occurring within the next seven days.
Each event should display:
•	School name.
•	Event type.
•	Date and time.
•	Current status.
•	A link to the school's details.
Events should be ordered chronologically, with the earliest event appearing first.
Events that are overdue must be visibly distinguished from future events.
The dashboard should not become a calendar containing months of historical activity. Older events belong in the appointments section.
C. Acquisition pipeline
Display a compact section showing schools currently being approached for appointments or demonstrations.
Each entry should identify:
•	School name.
•	Current acquisition stage.
•	Next scheduled action, if one exists.
•	Date of the next action.
This section should help the founder identify which schools need attention without opening every school record.
D. Empty states
The dashboard must remain useful when no information has been entered.
For example:
•	No upcoming appointments: "No upcoming appointments."
•	No follow-ups due: "You're up to date on follow-ups."
•	No schools registered: "Add your first school to begin."
Provide a direct action button where appropriate.
 
3. My Schools
This section contains the complete list of schools known to the application.
Every school must have an individual record.
3.1 School cards
Display schools as cards rather than a long, dense table.
Each card should contain only the most useful information:
•	School name.
•	Location or area.
•	Acquisition status.
•	Next appointment or follow-up, if available.
•	Customer classification.
The card should visually distinguish schools that are prospects from schools that have become customers.
For example:
Example Secondary School
Location: Dar es Salaam
Status: Demo Scheduled
Next action: Demonstration on 24 October
Classification: Prospect
[View School]
The example is illustrative.
Card behavior
When a card is clicked, open the detailed record for that school.
The card itself should not contain the entire history of the school's relationship with DrDemic.
That information belongs on the school's detail page.
3.2 School search and filtering
The list must support:
•	Searching by school name.
•	Filtering by acquisition status.
•	Filtering by customer classification.
Useful filters include:
•	All Schools
•	New Prospects
•	Appointment Pending
•	Demo Scheduled
•	Follow-up Required
•	Paying Customers
•	Not Proceeding
Search and filtering must work without requiring the founder to scroll through the entire collection.
3.3 Adding a school
The founder must be able to register a school quickly.
The initial form should request only:
Required
•	School name.
Optional
•	Location or area.
•	Contact person's name.
•	Contact person's phone number.
•	Brief note.
The founder must be able to save a school without completing every optional field.
Do not require the founder to answer questions about the school's budget, number of students, existing software, decision-making structure, or other business characteristics during registration.
Those details can be recorded later if they become genuinely necessary.
3.4 Duplicate prevention
The application should warn the founder when a school with a similar name already exists.
Where possible, use the combination of school name and location to help identify potential duplicates.
The warning should allow the founder to open the existing record rather than creating another one accidentally.
 
4. School Detail Page
Every school must have a dedicated detail page.
This page is the central record of the relationship between the founder and that school.
It must answer:
•	Who is this school?
•	What is its current relationship with DrDemic?
•	What happened during previous interactions?
•	What should happen next?
•	Is it already a customer?
4.1 School information
The top of the page should display:
•	School name.
•	Location.
•	Contact information, if available.
•	Current acquisition status.
•	Customer classification.
The acquisition status and customer classification must be separate fields.
For example, a school can be a paying customer while still having an upcoming product demonstration or review meeting.
4.2 Acquisition status
Use the following initial status options:
Status	Meaning
New Prospect	The school has been registered but has not yet been meaningfully approached.
Contacted	Initial contact has been made.
Appointment Pending	An appointment has been requested or is being arranged.
Appointment Scheduled	A meeting has been agreed upon and scheduled.
Demo Scheduled	A demonstration has been arranged.
Demo Completed	The demonstration has taken place.
Follow-up Required	Another action is needed to move the relationship forward.
Trial or Evaluation	The school is testing or evaluating DrDemic.
Paying Customer	The school has become a paying customer.
Not Proceeding	The school has declined or the acquisition effort has been stopped.
The founder must be able to change a school's status manually.
The system should not automatically mark a school as a paying customer merely because a demonstration was completed or the school expressed interest.
A payment or verified business decision must justify the change.
The status options should remain configurable in the future, but the first version can use a fixed list.
4.3 Customer classification
Maintain a separate field:
•	Prospect
•	Free Customer
•	Paying Customer
•	Former Customer
The distinction is important.
A school using a free version of DrDemic is not necessarily a paying customer.
Similarly, a former customer should not be counted as an active paying customer.
For the first version, the founder may update this classification manually.
Later, it may be integrated with DrDemic's subscription and payment records.
4.4 Next action
Every school should have an optional next-action field.
Examples:
•	Call the headmaster.
•	Arrange a demonstration.
•	Send the updated score-sheet link.
•	Return for a follow-up meeting.
•	Confirm whether the school wants to proceed.
The next action should include an optional date and time.
When the date and time are set, the action should appear on the dashboard at the appropriate time.
When no next action exists, display "No next action scheduled."
Do not force the founder to create a next action after every interaction.
4.5 Interaction history
The school detail page should contain a chronological history of important interactions.
Each entry should contain:
•	Date and time.
•	Brief note.
•	Optional interaction type.
Example:
20 October 2026
Visited the school. The headmaster was unavailable. A follow-up visit may be necessary.
The system should record when the entry was created.
The founder should be able to add, edit, and review notes.
Keep the interaction history separate from the school's current status. Updating the status must not erase the history of previous interactions.
 
5. Quick Interaction Recording
This is one of the most important parts of the application.
The system must not behave like a survey or customer relationship management form containing dozens of mandatory questions.
After a conversation with a school representative, the founder should be able to record the outcome with minimal effort.
5.1 Quick note interface
Provide a simple action labeled "Record Interaction."
When clicked, display a compact form containing:
Interaction type
•	Visit
•	Phone Call
•	WhatsApp
•	Demonstration
•	Meeting
•	Other
Quick note
A single text area for a short description of what happened.
Next action
An optional field describing what should happen next.
Follow-up date
An optional date and time.
Save
A single button to save the interaction.
The date and time of the interaction should be generated automatically.
The founder should not need to enter information that the application already knows.
5.2 Quick status updates
Provide a separate action to change the school's acquisition status.
For example, the founder should be able to change a school from "Contacted" to "Appointment Scheduled" without opening a large editing form.
When an appointment is created, the application should offer to update the school's status where appropriate.
The founder must remain in control of the final change.
5.3 Interaction design rules
The system must not:
•	Require a questionnaire after every visit.
•	Require a note when the founder only needs to update a status.
•	Require an appointment for every school.
•	Force the founder to fill in optional contact information.
•	Automatically create follow-up tasks without a clear reason.
•	Ask for information that already exists in the database.
The goal is to capture useful information, not to collect data for its own sake.
 
6. Appointments and Events
The application must provide a dedicated appointments section.
It should support meetings, demonstrations, scheduled calls, and follow-up activities.
6.1 Creating an appointment
An appointment should contain:
•	School.
•	Appointment title or type.
•	Date and time.
•	Optional location.
•	Optional note.
•	Status.
The school must be selected from the existing school records.
If the school does not exist, the founder should be able to create its record first.
Appointment types may include:
•	Initial Meeting
•	Demonstration
•	Follow-up Meeting
•	Phone Call
•	Product Review
•	Other
6.2 Appointment status
Use these initial values:
•	Scheduled
•	Completed
•	Cancelled
•	Missed
The founder should be able to update an appointment's status.
An appointment must not automatically become completed simply because its scheduled time has passed.
If an appointment's time passes without the founder updating it, the system should identify it as requiring attention.
A scheduled appointment that has already passed can be shown as overdue or awaiting an outcome.
6.3 Upcoming appointments
The appointments section should provide views for:
•	Today
•	Next Seven Days
•	All Upcoming
•	Past Appointments
Past appointments should remain available for reference.
Cancelled appointments should not appear as upcoming actionable events.
Completed appointments should remain in the school's interaction history.
6.4 Appointment reminders
The initial version should display reminders inside the application.
For example:
•	Appointment in 30 minutes.
•	Appointment tomorrow.
•	Appointment overdue.
•	Follow-up due today.
Reminder timing should eventually be configurable.
Do not begin with SMS, email, or WhatsApp notifications. Those integrations introduce additional dependencies and complexity.
First make the in-application reminder system reliable.
 
7. Dashboard Alert System
The dashboard must highlight events that require attention.
It should not overwhelm the founder with notifications about every record in the database.
7.1 Event display window
By default, display actionable events occurring from the current time through the next seven days.
The founder should be able to see:
•	Upcoming appointments.
•	Follow-ups due.
•	Overdue appointments requiring an outcome.
•	Other scheduled acquisition activities.
Events must be sorted by urgency and time.
Overdue items should be clearly distinguished from future events.
7.2 Alert rules
Implement the following initial rules:
Appointment approaching
If an appointment is scheduled within the next 30 minutes, show an alert.
Appointment tomorrow
Show appointments occurring within the next 24 hours in the upcoming-events section.
Follow-up due
If a scheduled follow-up date is today or earlier and the action is not completed, show it as requiring attention.
Overdue appointment
If a scheduled appointment has passed without being marked completed, cancelled, or missed, flag it for review.
These rules should be calculated from stored appointment and follow-up dates rather than maintained as manually updated alert records.
That prevents alerts from becoming stale when appointment times change.
7.3 Avoiding duplicate alerts
An appointment should not generate multiple identical alert entries on every page refresh.
For the initial version, alerts can be calculated dynamically and displayed in the dashboard.
Persistent notification history is unnecessary unless a later requirement justifies it.
7.4 Time handling
Use the local time zone for Dar es Salaam when displaying appointments.
Store timestamps consistently in the database, preferably in UTC, and convert them to local time for display.
This prevents confusion when dates or time zones are handled differently by the application environment.
 
8. Data Model
Use SQLite for the initial database.
The database should contain three primary tables:
1.	Schools
2.	Interactions
3.	Appointments
A fourth table for follow-up tasks may be introduced if the implementation requires follow-ups to be managed independently from interactions.
8.1 Schools table
Suggested fields:
Field	Purpose
id	Unique school identifier.
name	School name.
location	School area or location.
contact_name	Contact person's name, if known.
contact_phone	Contact person's phone number, if known.
acquisition_status	Current acquisition stage.
customer_type	Prospect, free customer, paying customer, or former customer.
next_action	Brief description of the next intended action.
next_action_at	Optional scheduled date and time.
notes	Optional general note.
created_at	Record creation timestamp.
updated_at	Last modification timestamp.
The id field must be the primary key.
School names should not be used as database identifiers because names may change and duplicate names are possible.
8.2 Interactions table
Suggested fields:
Field	Purpose
id	Unique interaction identifier.
school_id	Reference to the school.
interaction_type	Visit, call, WhatsApp, demonstration, meeting, or other.
note	Short description of the interaction.
created_at	Date and time the interaction was recorded.
The school_id field must reference the corresponding record in the Schools table.
One school may have many interactions.
Deleting a school must not accidentally destroy historical information without an intentional deletion policy.
For the initial version, consider preventing deletion of schools that have associated appointments or interactions. Allow the founder to mark them as inactive instead.
8.3 Appointments table
Suggested fields:
Field	Purpose
id	Unique appointment identifier.
school_id	Reference to the school.
title	Short appointment title.
appointment_type	Meeting, demonstration, follow-up, call, or other.
scheduled_at	Appointment date and time.
location	Optional meeting location.
note	Optional appointment note.
status	Scheduled, completed, cancelled, or missed.
created_at	Record creation timestamp.
updated_at	Last modification timestamp.
The database should enforce the relationship between appointments and schools.
An appointment must not refer to a school that does not exist.
8.4 Data integrity
The application must:
•	Use unique identifiers for records.
•	Validate required fields.
•	Validate date and time inputs.
•	Use parameterized SQL queries.
•	Enforce foreign-key relationships.
•	Prevent invalid status values.
•	Handle database errors gracefully.
•	Preserve records when unrelated fields are edited.
Use database constraints where appropriate rather than relying entirely on the interface to prevent invalid data.
 
9. Interface Design
The application should be clean, practical, and easy to use on both a laptop and a mobile phone.
The founder may need to access it immediately after leaving a school.
9.1 General layout
Use a simple layout with:
•	Navigation.
•	Page title.
•	Main content.
•	Primary action button.
Avoid unnecessary animations, decorative charts, and complicated navigation.
9.2 School cards
Cards should be readable at a glance.
Each card should have:
•	School name as the main heading.
•	Status badge.
•	Customer classification badge.
•	Location.
•	Next action, if available.
Use consistent visual styles for status badges.
Color must not be the only way to communicate status. Include readable text labels.
9.3 Mobile usability
The application must support narrow screens.
Requirements include:
•	Responsive card layouts.
•	Readable text.
•	Large enough buttons.
•	Compact forms.
•	Minimal horizontal scrolling.
•	Date and time inputs that work on mobile devices.
The application should not require a separate mobile application for the first release.
 
10. Technical Architecture
Use a simple, maintainable structure.
Suggested project layout:
drdemic-acquisition-tracker/
│
├── app.py
├── database.py
├── requirements.txt
│
├── instance/
│   └── acquisition.db
│
├── templates/
│   ├── base.html
│   ├── dashboard.html
│   ├── schools.html
│   ├── school_detail.html
│   ├── appointments.html
│   └── settings.html
│
├── static/
│   ├── css/
│   │   └── style.css
│   │
│   └── js/
│       └── main.js
│
└── tests/
    ├── test_schools.py
    ├── test_appointments.py
    └── test_dashboard.py
This is a proposed structure, not a requirement to create every file on the first day.
Begin with fewer files if that helps you understand the architecture. Split the application into modules as its responsibilities grow.
10.1 Python and Flask
Flask should handle:
•	HTTP routes.
•	Form submissions.
•	Request validation.
•	Communication with the database.
•	Rendering HTML templates.
Business logic should be kept separate from HTML templates where practical.
For example, the logic for finding upcoming appointments should not be duplicated in several templates.
10.2 SQLite
SQLite will store the application's data locally.
It is suitable for an initial single-user application and avoids the need to configure a separate database server.
Use transactions for operations that update related records.
For example, if completing an appointment also creates an interaction record, the operation should not leave the database in a partially updated state if an error occurs.
10.3 HTML, CSS, and JavaScript
HTML defines the page structure.
CSS handles the layout and appearance.
JavaScript may provide small interface improvements, but essential operations should not depend unnecessarily on complex client-side code.
Use normal Flask forms and server-side validation for the initial implementation.
10.4 Configuration and security
The application should:
•	Keep its database outside publicly served static files.
•	Protect against SQL injection using parameterized queries.
•	Validate and escape user-provided content.
•	Use Flask's security features appropriately.
•	Keep secret configuration outside source code.
•	Avoid exposing debug mode when deployed.
•	Maintain database backups.
If the application is accessible over a public network, add appropriate authentication before storing real school contact details.
 
11. Development Roadmap
Implement the system in small, testable stages.
Do not begin by implementing the entire specification.
Phase 1: Project foundation
Tasks:
1.	Create the project directory.
2.	Create a Python virtual environment.
3.	Install Flask.
4.	Create a minimal Flask application.
5.	Display a basic dashboard.
6.	Configure Git version control.
Completion criteria: The application starts successfully and displays a page in the browser.
Phase 2: School management
Tasks:
1.	Create the Schools table.
2.	Implement school registration.
3.	Display schools as cards.
4.	Implement school search.
5.	Implement school details.
6.	Allow school information to be edited.
7.	Add acquisition status and customer classification.
Completion criteria: The founder can register, find, open, edit, and classify schools.
Phase 3: Interaction history
Tasks:
1.	Create the Interactions table.
2.	Add the quick interaction form.
3.	Save interaction notes.
4.	Display interaction history.
5.	Validate submitted data.
Completion criteria: The founder can record a school visit quickly and review it later.
Phase 4: Appointments
Tasks:
1.	Create the Appointments table.
2.	Add appointment creation.
3.	Display upcoming appointments.
4.	Update appointment status.
5.	Associate every appointment with a school.
6.	Display appointments on the school detail page.
Completion criteria: The founder can schedule and manage appointments without maintaining a separate notebook for the same information.
Phase 5: Dashboard intelligence
Tasks:
1.	Display summary cards.
2.	Retrieve upcoming appointments.
3.	Identify overdue follow-ups.
4.	Flag appointments that require attention.
5.	Display the acquisition pipeline.
6.	Handle empty states.
7.	Test date and time boundaries.
Completion criteria: Opening the dashboard reveals the most important upcoming activities without requiring manual searching.
Phase 6: Usability and reliability
Tasks:
1.	Improve the mobile layout.
2.	Test forms with missing or invalid data.
3.	Test duplicate-school warnings.
4.	Test database relationships.
5.	Verify that completed and cancelled appointments are handled correctly.
6.	Implement a database backup procedure.
7.	Review basic security.
Completion criteria: The application is reliable enough for regular personal use.
 
12. Testing Requirements
Testing must accompany development rather than being postponed until the end.
The following behaviors must be verified.
School management
•	A school can be registered with only its name.
•	Optional fields can remain empty.
•	Schools persist after the application restarts.
•	A school can be found through search.
•	Editing a school does not create a duplicate.
•	A school can be classified as a paying customer.
•	Similar school records trigger a duplicate warning.
Interaction history
•	An interaction can be saved with a short note.
•	Its timestamp is generated automatically.
•	Interactions appear under the correct school.
•	Editing school information does not erase interaction history.
Appointments
•	An appointment can be scheduled for an existing school.
•	Invalid dates are rejected.
•	An appointment cannot reference a nonexistent school.
•	Cancelled appointments do not appear as actionable upcoming events.
•	Completed appointments remain available in the history.
•	Past appointments that remain scheduled are flagged for review.
Dashboard
•	Upcoming events appear in chronological order.
•	Events outside the seven-day display window do not appear in the default view.
•	Overdue follow-ups are visible.
•	A school with no upcoming events does not cause an error.
•	An empty database produces a useful dashboard.
•	Changing an appointment's time updates the dashboard correctly.
 
13. Features Deliberately Excluded From the First Version
The initial release will not include:
•	Machine learning.
•	AI-generated sales recommendations.
•	Automatic WhatsApp messages.
•	SMS reminders.
•	Email notifications.
•	Payment processing.
•	Multiple user roles.
•	School employee management.
•	Complex analytics.
•	Automated lead scoring.
•	External CRM integrations.
•	Mandatory post-visit questionnaires.
•	Complicated reporting tools.
These features may be considered later if actual usage demonstrates a need for them.
The absence of a feature is not a failure if the application accomplishes its primary purpose without it.
 
14. Future Development Principles
The application should evolve according to actual experience.
After using it during school visits, the founder may discover that certain fields are unnecessary or that an important workflow is missing.
Changes should be based on real needs.
Before adding a feature, ask:
1.	What problem does this feature solve?
2.	How frequently does that problem occur?
3.	Can the existing system solve it more simply?
4.	Will the feature create additional work?
5.	Is the feature worth maintaining?
The data collected during normal acquisition work may eventually support more advanced analytics or machine learning.
However, no future feature should make the basic workflow slower without a clear benefit.
 
15. Definition of Success
The first version will be considered successful when the founder can:
1.	Register a school in a few seconds.
2.	Find any registered school quickly.
3.	Open a school card and understand its current status.
4.	Determine whether it is a prospect, free customer, or paying customer.
5.	Record a short interaction without completing a questionnaire.
6.	Schedule and manage appointments.
7.	See upcoming appointments and overdue follow-ups on the dashboard.
8.	Understand what requires attention without reviewing every school record.
9.	Close the application and return later without losing data.
10.	Maintain the system without needing to become a full-time administrator of the system itself.
The governing principle is simple: the tracker exists to support school acquisition, not to become another job.
